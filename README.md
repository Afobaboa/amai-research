# АМАИ РАЗРАБОТКА

Система учёта рецептур и экспериментов на Django. Начальный набор БД содержит реальные данные из Excel по трём сериям: «Зимняя пена», «Зимняя улучшенная пена» и «Зимняя пена с фреоном». Вымышленные рецептуры и результаты удалены из начального набора. Справа доступен ИИ-ассистент через Cloud.ru; для ответов нужен серверный API-ключ.

Приложение использует утверждённое документальное ядро: версии рецептур и план заправки, эксперименты, группы измерений с показателями, результаты, наблюдения, обработка и происхождение данных. Физические объекты, фактические навески и операции изготовления в этот этап не входят.

Создание рецептуры разделено на полиольную смесь, необязательный изоцианат
и газовую смесь. Расчёт навесок и заправки выполняется при вводе и повторяется
на сервере при сохранении; расчётные значения изменить вручную нельзя.
Поддерживаются исходные режимы A:B → ISO index и ISO index → A:B.
Каждое отсутствующее исходное значение требует причины; причины отсутствия
результатов формируются из зависимостей. Подробнее: [редактор рецептур](docs/recipe-editor.md).

Начальные данные включают все исходные параметры 135 зимних рецептур,
исторические свойства и настройки округления из Excel. Существующий
облачный инициализатор выполняет `migrate` и `seed_initial`, поэтому при
первом деплое новый редактор сразу получает заполненные рецептуры.
При обновлении существующей установки выполнить `make upgrade-data`:
новая миграция добавляет документ исходных параметров, повторный импорт
дополняет неизменённый архив и сохраняет пользовательские правки.

Рабочие возможности: три зимние серии, источники и вложения, справочники
материалов и партий, группы измерений, редактор рецептур и сохранённые расчёты.
Для повторного использования состава создают новую версию из карточки рецептуры;
разделы шаблонов рецептур и расчётов удалены. [Описание возможностей и истории
изменений модели](docs/functionality-v1.1.md).

## Эксперименты и группы измерений

В разделе «Группы измерений» создаются общие наборы показателей.
Начальные группы: «Основные параметры», «На бумаге», «В форме»,
«Проверка баллона» и «Дополнительные показатели». Один показатель может
входить в несколько групп. Название и состав группы редактируются в справочнике.

В «Основных параметрах» находятся температура и влажность. Давление,
встряхиваемость и измерения массы входят в «Проверку баллона».

В эксперименте нажмите «Добавить группу измерений», выберите группу и заполните
известные значения. Наблюдение можно записать вместе с группой. Для каждого показателя нужно ввести значение или причину отсутствия
измерения. Без обоих форма не сохраняется; введённый ноль считается значением.
Кнопка «Заполнить показатели» позволяет дописать значения; записи из источников
и расчётов защищены от изменений. Группу можно добавить повторно для нового
набора измерений. Читатель и завершённый эксперимент доступны для просмотра.

При обновлении `make upgrade-data` сохраняет копию SQLite и применяет миграции.
Миграции 0013–0015 связывают прежние определения с общим справочником,
переименовывают «Параметры карточки» в «Основные параметры» и переносят
условия в результаты этой группы. Идентификаторы прежних результатов,
наблюдения, расчётные зависимости и ссылки на первичные ячейки сохраняются.
Отдельная форма условий удалена. Новые адреса используют `/experiments/`;
старые `/tests/` перенаправляются с сохранением параметров запроса.
Технические имена `TestSession` и `TestRun` сохранены для совместимости данных.
Архивные Excel и JSON остаются первичными источниками с исходной терминологией.

## Компактные рабочие экраны

Рабочие экраны следуют табличному редактору рецептур: компактная шапка,
таблицы на всю ширину, связанные данные и история в видимых блоках рядом.
Вкладки не используются: данные доступны одновременно. На компьютере
длинные списки прокручиваются внутри таблицы с закреплёнными заголовками;
поиск, действия и номера страниц остаются рядом. «На весь экран» скрывает
навигацию и ассистента до повторного нажатия или Escape.

В карточке эксперимента группы измерений раскрываются на полную высоту:
все показатели и наблюдения видны без внутренней вертикальной прокрутки.
Карточки располагаются плиткой: следующая занимает свободное место под
короткой карточкой. Число колонок зависит от доступной ширины.

В группах измерений значение, единица, причина отсутствия и происхождение
показаны в одной строке. Enter / Shift+Enter перемещают фокус по столбцу,
стрелки вверх/вниз — между числовыми полями. После сохранения открывается
раздел изменённой группы, наблюдения или обработки. Ссылки на исходные
ячейки ведут к нужной строке. На touch-экранах сохранены крупные поля;
без JavaScript все разделы доступны последовательно.

Общая раскладка находится в `workspace.css` и
`lab/frontend/workspace.ts`, ввод измерений — в `measurements.css` и
`lab/frontend/measurements.ts`. Браузерная проверка `npm run test:workspace`
использует временную БД, проверяет 1366×768, прямые ссылки, сохранение,
черновики, клавиатуру, полноэкранный режим и touch-экраны.

## Стиль кода и постепенный рефакторинг

Старайтесь сохранять строки короткими: ориентир — до 88 символов.
Длинные выражения и строковые литералы переносите по смыслу; не сжимайте
несколько действий в одну строку ради лимита.

Функции и методы должны занимать не более 30 строк, включая сигнатуру
и пустые строки внутри. Выделяйте самостоятельные шаги в понятные функции.
Существующий код приводите к этим правилам лениво: при изменении функции
рефакторьте её в рамках той же задачи. Не затрагивайте остальные функции
только ради форматирования. Генерируемые миграции сохраняйте в формате Django.

## Локальная разработка: бэкенд и фронт

В текущей архитектуре Django обслуживает серверную логику и HTML-интерфейс.
Оформление следует правилам AMAI из `amai-ui/`: тема и компоненты подключены
перед стилями LIMS, без внешних шрифтов и CDN. Браузерная логика написана
на TypeScript в `lab/frontend/`, со строгой проверкой типов DOM и ответов API.
Скомпилированные JS, включая `lab/static/lab/app.js`, `assistant.js`
и `recipe-editor.js`, хранятся в проекте,
поэтому для запуска готового приложения достаточно Python 3.13+.
Для изменения TypeScript и браузерных тестов нужен Node.js 20+.

После изменения `.ts` выполните из папки `LIMS`:

```bash
npm ci                  # установка зависимостей из lock-файла
npm run typecheck       # строгая проверка типов без записи файлов
npm run build           # сборка JS для Django и Docker
npm run dev:frontend    # автоматическая пересборка при изменении TS
```

Режим `dev:frontend` запускается в отдельном терминале рядом с `make dev`.
Сгенерированные JS-файлы нужно сохранять вместе с TS; напрямую их не меняют.
CSS и Django-шаблоны доступны после обновления страницы без пересборки.
Исходный UI-пакет остаётся в `amai-ui/`, его канонические CSS скопированы
в `lab/static/lab/`; адаптация LIMS находится в `app.css` и `assistant.css`.

Одиночные списки выбора используют `lab/frontend/search-select.ts`: поиск
по части названия, клавиатура, сброс необязательного значения и поддержка
добавляемых строк формы. Их оформление находится в `lab/static/lab/search-select.css`.
В составе рецептуры сначала выбирают компонент: список партий показывает только
его партии. При смене или сбросе компонента прежняя партия сбрасывается.
Выбор сохраняется при обновлении страницы, редактировании и копировании рецептуры.
Адреса CSS и JS содержат версию содержимого, чтобы браузер обновлял файлы
после изменений. Если стили списка не загрузились, остаётся обычный select.
Реестры, списки, история диалогов и поиск ассистента
не учитывают регистр и считают пробелы, `-`, `_`, `.` одинаковыми:
`ep z` и `ep_z` находят `TEP-Z`. Повторяющиеся разделители также равнозначны.
Нормализация меняет только поиск, исходные обозначения сохраняются.
Поиск в реестрах обновляет список после 250 мс без ввода, сохраняя фокус,
фильтры и адрес страницы. Кнопка «Найти» запускает поиск сразу.
Браузерная логика реестров находится в `lab/frontend/live-search.ts`;
без JavaScript формы продолжают работать обычными GET-запросами.
Рядом с редактированием рецептур, испытаний и партий доступна отдельная
форма смены статуса с проверкой прав, ограничений и записью в историю.

Из папки `LIMS`:

```bash
make setup          # создаёт .venv, ставит зависимости и загружает реальные данные
make dev            # запускает бэкенд и фронт локально
```

Открыть <http://127.0.0.1:8000/>. Локальный пароль — `lims-demo`; затем выбрать профиль. **Гущин Даниил** — автор, **Иван Иванов** — читатель. Автор может создавать записи; читатель — только просматривать. Выбор ФИО фиксирует выбранное авторство и не подтверждает личность, как согласовано для пилота. Другой порт: `make dev PORT=8001`. Остановка — `Ctrl+C`.

Используется отдельный профиль `config.local`: SQLite в `var/local.sqlite3`, HTTP на loopback, локальный пароль. Он игнорирует production-переменные `DATABASE_URL`, `SITE_PASSWORD_HASH`, `SECRET_KEY`, `DEBUG`, `DEMO_MODE`, `ALLOWED_HOSTS` и прежний `SQLITE_PATH`. Существующая база `var/lims.sqlite3` и облачная БД не используются. Рабочие настройки Docker по-прежнему находятся в `config.settings`.

Начальные данные и профили сотрудников загружаются командой `make setup` или `make init-data` (команда Django — `seed_initial`). Повторное заполнение не дублирует набор и не сбрасывает внесённые изменения. Запуск `make dev` сам не мигрирует и не заполняет БД. После добавления миграций выполнить `python3 scripts/local.py manage migrate`. Изменения Python-кода перезапускают dev-сервер; изменения шаблонов, CSS и JavaScript видны после обновления страницы.

Сохранённые записи переживают перезапуск. Для дополнительной локальной базы можно явно задать `LIMS_LOCAL_DB=/absolute/path/to/another.sqlite3`; её нужно отдельно подготовить командой `make init-data` с той же переменной. Удалять существующую базу для обычного запуска не требуется. Начальный набор подготовлен из Excel заранее: веб-сервер не перечитывает архив при каждом запуске, исходники Excel и Parquet не изменяются.

Если `make` не установлен, эквивалентные команды работают напрямую, включая Windows с `python` вместо `python3`:

```bash
python3 scripts/local.py setup
python3 scripts/local.py dev --port 8000
```

Для работы с серверной логикой доступны Django shell и административный пользователь локальной базы:

```bash
python3 scripts/local.py manage shell
python3 scripts/local.py manage createsuperuser
```

## Админка и обратная связь

При работающем `make dev` административная панель доступна по адресу
<http://127.0.0.1:8000/admin/>. Если задан другой порт, используйте его.
Вход выполняется по имени пользователя и паролю Django, созданным командой
`python3 scripts/local.py manage createsuperuser` из папки `LIMS`.
Общий пароль `lims-demo` и выбор профиля сотрудника относятся к основному
приложению; для админки нужна отдельная учётная запись.

Кнопка «Обратная связь» справа в верхней строке рабочего пространства
открывает форму сообщения. Отправлять сообщения могут авторы и читатели.
После отправки текст сохраняется в БД вместе с выбранным сотрудником,
его ФИО на момент отправки и временем. Ограничение — 5000 символов;
пустые сообщения не принимаются. После успешной отправки открывается
обзор лаборатории с подтверждением.

Для просмотра откройте в админке раздел «Обратная связь» или сразу
<http://127.0.0.1:8000/admin/lab/feedback/>. В списке видны дата,
сотрудник и начало сообщения; нажмите на дату, чтобы прочитать полный текст.
Доступны поиск по тексту и ФИО, фильтр по дате. Содержимое сообщения
в админке доступно только для чтения.

После обновления существующей локальной установки примените миграцию:

```bash
python3 scripts/local.py manage migrate
```

В Docker админка находится по пути `/admin/` на домене приложения.
Обновление `docker compose up -d --build` применяет миграции автоматически.
Администратора этой БД создают отдельно:

```bash
docker compose exec web python manage.py createsuperuser
```

## Начальные данные из Excel

Версионируемый набор [initial_data/winter.json](initial_data/winter.json)
подготовлен из трёх книг рецептур и трёх соответствующих книг испытаний:
зимняя пена (302), зимняя улучшенная пена (316)
и зимняя пена с фреоном (316-Ф). Скрипт
[scripts/build_initial_data.py](scripts/build_initial_data.py) воспроизводит
подготовку набора; [initial_data/winter-report.json](initial_data/winter-report.json)
содержит результаты проверки качества и ограничения переноса.

Все шесть исходных Excel включены в [initial_data/sources/](initial_data/sources/README.md)
и скачиваются из списка и карточки источника. Исторические пути `Пена/pena/`
и SHA-256 сохранены, но для запуска сервера и скачивания достаточно папки LIMS.
Docker проверяет комплектность и контрольные суммы книг при сборке.

В наборе 135 версий рецептур и 167 карточек испытаний из 302 листов.
У 158 испытаний однозначно установлена связь с рецептурой; у 6 остаются
несколько кандидатов, для 3 рецептура отсутствует в исходных книгах.
Повторная загрузка обновляет связи существующих карточек, сохраняя
отклонения и рецептуры, выбранные сотрудником. Для локальной базы
используйте `make upgrade-data` с предварительным резервным копированием.
Сохранены 72 739 первичных фрагментов, включая 54 комментария Excel.
Материалы нормализованы отдельно от партий: 72 материала и 124 партии.
Перенесены цены в EUR/кг по указанию пользователя и плотности компонентов,
изоцианатов и газов. Архивные расчёты используют собственные исторические
значения; свойства партий содержат последние датированные значения с
происхождением. В карточке материала цены и плотности отсутствуют: они
показываются у конкретных партий. Цена TEP-Z для `302.84` по указанию
пользователя перенесена из `302.83!C12` с явным основанием переноса.
Вкладка «Категории материалов» заполнена семью функциональными группами;
все 72 материала распределены по ним. [Классификация и основания](initial_data/material-categories.json)
загружаются вместе с остальными начальными данными. Неоднозначные марки
отнесены к добавкам, тип которых требует уточнения.
Проверить воспроизводимость из корня репозитория (нужно окружение анализа
из `Пена/`): `Пена/.venv/bin/python LIMS/scripts/build_initial_data.py --check`.

Команда `seed_initial` загружает этот подготовленный набор в БД.
Сохранённые ссылки на книгу, лист и ячейку позволяют сверить данные
с оригиналом. В карточке источника выбирается лист; фрагменты показаны
по 150 на странице. Ссылка на ячейку открывает нужную страницу. Исходные комментарии, пропуски и ошибки формул сохраняют
свой смысл; недостающие цены, плотности и партии не выдумываются.
Профиль Гущина Даниила фиксирует автора загрузки в LIMS,
а не предполагаемого автора исторических лабораторных записей.

## ИИ-ассистент справа

Помощник обсуждает эксперименты и гипотезы, ищет материалы, рецептуры и результаты в текущей БД и читает разрешённые исходники интерфейса/документацию для объяснения сайта. Инструменты работают только на чтение; ссылки в ответах ведут к исходным карточкам. Помощник читает реальные записи из текущей БД и их источники.

Для подключения создайте API-ключ **Cloud.ru Foundation Models** и запишите его **Key Secret** в `LIMS/.env`:

```dotenv
CLOUD_RU_API_KEY='вставьте_сюда_Key_Secret'
CLOUD_RU_MODEL=deepseek-ai/DeepSeek-V4-Pro
CLOUD_RU_BASE_URL=https://foundation-models.api.cloud.ru/v1
```

Примените миграции: `python3 scripts/local.py manage migrate`, затем перезапустите `make dev` (он запускает веб-сервер и обработчик очереди). Для Docker выполните `docker compose up -d --build`: Compose сначала применяет миграции и загружает начальные данные, затем запускает веб-сервер и обработчик очереди. Проверка доступных моделей: `python3 scripts/local.py manage assistant_models` или `docker compose exec web python manage.py assistant_models`. Ключ хранится на сервере; без него остальное приложение продолжает работать.

[Пошаговое получение ключа, параметры, доступ к БД/коду и диагностика](docs/assistant.md). Сведения из диалога и выбранные для ответа данные отправляются через Cloud.ru; диалоги и ответы сохраняются в БД с привязкой к сотруднику. Между диалогами можно переключаться; генерация выполняется отдельным процессом и продолжается после перезагрузки или закрытия вкладки.

## Что проверять в интерфейсе

- Обзор лаборатории и переход к рецептурам и карточкам испытаний.
- Поиск и фильтры в реестрах, просмотр состава, условий и результатов.
- Создание рецептуры и новой версии, создание карточки, ввод результатов и наблюдений. В новой карточке первым полем обязательно выбирается опубликованная рецептура; номер карточки равен её обозначению и вручную не вводится. Несколько испытаний одной рецептуры могут иметь одинаковый номер и разные внутренние ID. Основание связи удалено, лист источника в форме карточки не выбирается; архивные ссылки на источники сохраняются.
- Редактирование и публикация черновика рецептуры. Опубликованная версия фиксируется; изменения состава сохраняются новой версией.
- Завершение карточки испытания: после завершения она и результаты доступны для просмотра.
- Просмотр истории с выбранным автором и временем изменений.
- Работа читателя: просмотр доступен, изменяющие запросы отклоняются сервером.
- Создание источника: файл, ссылка или запись; разделы и первичные фрагменты, выбор источника в рецептуре и первичных ячеек при записи результатов.
- Справочники материалов и партий: свойства, цена, поставщик, паспорт, срок годности, статусы «Доступна» и «Закрыта», прослеживаемость использования.
- Повторное использование рецептуры через создание новой версии из её карточки.
- Автоматически используются все расчёты: масса, аддитивный объём и плотность, стоимость и цена за кг; зафиксированный расчёт публикации и отдельный повторный расчёт.
- ИИ-ассистент справа: поиск данных и источников, обсуждение гипотез, объяснение навигации по действующему интерфейсу; состояние без ключа и ответы после подключения Cloud.ru.

Данные Excel сохраняют исходные обозначения и ссылки на источник. Пропуски не подменяются нулями; ошибки формул не считаются измерениями. Связь карточки с планом рецептуры не доказывает фактическое изготовление.

## Проверки

Серверные тесты, проверки миграций и проверки изоляции локальных настроек:

```bash
make test-backend
```

Браузерные тесты проверяют фронт с настоящим локальным бэкендом: формы и версии
рецептур, группы измерений и результаты, источники и вложения, партии и смену
их статуса, снимки расчётов, права, историю, перезагрузку страниц и мобильную
верстку. Отдельная проверка помощника покрывает диалог, источники, ошибки,
отмену, историю и доступность панели; ответы Cloud.ru в ней подменены.
Первоначальная установка браузера и запуск:

```bash
make setup-browser           # npm ci и установка Chromium; требуется Интернет
make test-frontend           # headless
make test-frontend-headed    # те же сценарии в видимом окне браузера
make test                    # серверные и браузерные тесты вместе
```

Без `make`: `python3 scripts/local.py test-backend`, `npm ci`, `npx --no-install playwright install chromium`, `npm run test:frontend` или `npm run test:frontend:headed`. На минимальном Linux-окружении при отсутствии системных библиотек Chromium установить зависимости командой `npx --no-install playwright install --with-deps chromium`.

Оба набора тестов используют временные SQLite-базы. Браузерный тест сам поднимает и останавливает собственный сервер на свободном порту и не обращается к серверу `make dev`. Можно явно задать `LIMS_BROWSER_PORT`; занятый порт приводит к отказу запуска теста. Рабочая локальная база `var/local.sqlite3` и прежняя `var/lims.sqlite3` не изменяются.

Снимки сохраняются в `var/browser-artifacts/` (переопределение: `LIMS_ARTIFACT_DIR`), снимки помощника — в `var/assistant-browser-artifacts/`. Для нестандартного окружения поддерживаются `LIMS_PYTHON` — путь к Python с Django и `KUDO_PLAYWRIGHT_MODULE` — явный путь к установленному Playwright. В обычной установке эти переменные не нужны. Только чат можно проверить командой `npm run test:assistant`.

Восстановление несохранённых форм после обновления проверяется отдельно:
`npm run test:forms` для Chromium и `npm run test:forms:firefox` для Firefox.
Для второго сценария сначала выполнить `npx --no-install playwright install firefox`.
Проверяются добавление и удаление строк, значения и даты, существующая карточка
испытания, ссылки на источники, ошибки валидации и очистка черновика после сохранения.
Firefox восстанавливает скрытые поля при перезагрузке независимо от динамических
строк; сравнение черновика с сервером использует отдельные исходные значения.

Для проверки настроек без запуска тестов: `make check`. Тесты и локальный сервер можно запускать одновременно в разных терминалах.

Настройка справочников и профилей сотрудников выполняется через Django admin. Технический администратор использует собственные учётные данные Django; выбор профиля автора не даёт административных прав.

## Подготовка облачного запуска

В репозитории подготовлены Docker Compose, PostgreSQL и Caddy. Работающий облачный сервер этим изменением не создаётся. Для размещения нужны сервер с Docker Compose, домен с DNS-записью на сервер, разрешённые внешние IP/подсети, общий пароль и список сотрудников с ролями.

```bash
cp .env.example .env
chmod 600 .env
```

Заполнить `.env`: `SITE_DOMAIN`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `ALLOWED_IPS`, `SECRET_KEY`, `POSTGRES_PASSWORD` и `SITE_PASSWORD_HASH`. Секреты и `.env` не добавлять в Git. `SECRET_KEY` и пароль PostgreSQL можно сгенерировать командами из `.env.example`. Для пароля PostgreSQL использовать hex-строку, чтобы не требовалось кодирование специальных символов в URL подключения.

Хеш общего пароля получить интерактивно в локальном окружении:

```bash
.venv/bin/python -c 'from getpass import getpass; from django.contrib.auth.hashers import PBKDF2PasswordHasher; h = PBKDF2PasswordHasher(); print(h.encode(getpass("Общий пароль: "), h.salt()))'
```

Скопировать хеш в `SITE_PASSWORD_HASH` в одинарных кавычках: они сохраняют символы `$` при чтении `.env` Docker Compose. Сам пароль в конфигурацию не записывается.

```bash
docker compose config --quiet
docker compose up -d --build
```

Compose ожидает готовности PostgreSQL и запускает служебный контейнер
`initialize`: он последовательно выполняет `migrate --noinput` и `seed_initial`.
После успешного завершения запускаются `web` и `assistant-worker`.
Если подготовка БД завершилась ошибкой, приложение и обработчик очереди
не запускаются; причина доступна в `docker compose logs initialize`.

Начальные данные включают три зимние серии, 135 версий рецептур,
167 карточек испытаний и профили Гущина Даниила (автор) и Ивана Иванова
(читатель). Повторный запуск распознаёт уже загруженные записи,
не создаёт дублей и сохраняет пользовательские правки рецептур и материалов.
Для последующих обновлений на продакшен-сервере используйте `make prod`
(описание ниже).
Конфигурация с `DEBUG=0` требует `DEMO_MODE=0`.

### Обновление продакшена одной командой

В каталоге `LIMS` на сервере:

```bash
make prod
```

Нужны Linux, Python 3, Git с доступом к `origin`, Docker с Compose,
поддерживающим `up --wait --wait-timeout`, и заполненный `.env`.
Команда развёртывает приложение **на том сервере, где её запустили**;
подключение по SSH к другому серверу она не выполняет.
`make dev` по-прежнему запускает локальную разработку.

`make prod` проверяет чистую рабочую копию на ветке `main`, получает
`origin/main` и обновляет исходники только fast-forward. Локальные коммиты,
которых нет в удалённом `main`, расхождение веток и незакоммиченные файлы
останавливают обновление. Одновременные запуски блокируются файловым замком.

Пока сайт работает, команда собирает образы и проверяет настройки Django
и Caddy. Затем останавливает Caddy, веб-сервер и обработчик ИИ, создаёт
согласованную копию PostgreSQL и вложений в `backups/prod-*/`, сохраняет
`.env` и идентификаторы коммитов. Каталог имеет права `700`, файлы — `600`;
маркер `COMPLETE` означает, что все части резервной копии сохранены.
Дамп дополнительно проверяется через `pg_restore --list`.

После этого выполняются миграции и идемпотентный `seed_initial`,
пересоздаются веб-сервер и обработчик ИИ. Команда ждёт готовности Django
по HTTP `/login/` и только затем пересоздаёт Caddy, чтобы обновились
его конфигурация и переменные окружения. Схема предполагает короткий
перерыв в доступности на копирование данных, миграции и запуск.
Проверка Django выполняется внутри контейнера; внешние DNS, TLS и доступ
с разрешённого IP нужно проверить отдельно.

PostgreSQL при обновлении не пересоздаётся; его версию и параметры
нужно менять отдельно. Тома с данными и сертификатами не удаляются.
Резервные копии автоматически не удаляются: следите за свободным местом
и переносите копии с сервера в защищённое хранилище.

Если сборка или предварительные проверки упали, работающие контейнеры
продолжают обслуживать сайт. При ошибке после начала остановки сайт
остаётся остановленным; команда выводит путь к резервной копии.
Проверьте сообщение об ошибке и `docker compose logs --tail=100 web assistant-worker caddy`,
исправьте причину и повторите `make prod`. При повторном запуске создаётся
новая копия — исходную копию до неудачной миграции сохраните отдельно.
Откат старого кода автоматически не выполняется: миграция могла частично
изменить схему БД. Для восстановления используйте полную копию с маркером
`COMPLETE` и процедуру ниже с пустой БД; `.env` содержит секреты.

При необходимости создать технического администратора после запуска:

```bash
docker compose exec web python manage.py createsuperuser
```

Дополнительные профили сотрудников можно создавать через `/admin/`.
Команды обслуживания через `docker compose run --rm --no-deps web ...`
сами не запускают подготовку БД.

Внешние порты открывает только Caddy. PostgreSQL и Django доступны внутри сети Compose; Caddy ограничивает доступ по реальному IP соединения ко всем путям, включая вход, admin и статику. Начальная allowlist допускает только loopback: заменить её своими адресами перед внешним просмотром. Список IPv4, IPv6 и CIDR в `ALLOWED_IPS` разделяется пробелами. После его изменения:

```bash
docker compose up -d --force-recreate caddy
```

Конфигурация рассчитана на прямые подключения к Caddy. Если перед ним появляется иной прокси, получение клиентского IP и доверенные прокси нужно настраивать отдельно. HTTPS выдаётся Caddy для указанного домена. Файлы PostgreSQL, вложения и сертификаты сохраняются в именованных томах. Миграции и начальные данные подготавливает `initialize`; статика собирается при запуске контейнера приложения.

## Резервное копирование и восстановление

Для резервной копии базы (из каталога `LIMS`):

```bash
mkdir -p backups
chmod 700 backups
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/lims.dump
docker compose run --rm --no-deps -v "$(pwd)/backups:/backup" --user root --entrypoint tar web -czf /backup/media.tar.gz -C /app/media .
```

Отдельно сохранить `.env` в защищённом месте. Для согласованной копии БД и файлов на время копирования остановить запись в приложение. Копии необходимо вынести с сервера.

Проверять восстановление следует на отдельном стенде с пустой БД, той же версией приложения и отдельными томами:

```bash
docker compose up -d db
docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --no-privileges' < backups/lims.dump
docker compose run --rm --no-deps -v "$(pwd)/backups:/backup:ro" --user root --entrypoint sh web -c 'tar -xzf /backup/media.tar.gz -C /app/media && chown -R lims:lims /app/media'
```

До `pg_restore` запускайте только `db`, без полного `docker compose up`:
иначе `initialize` создаст таблицы до восстановления дампа. Дамп уже
содержит схему и записи миграций. После восстановления выполните
`docker compose up -d --build`: служба `initialize` применит недостающие
миграции и проверит начальные данные. Затем проверьте вход, несколько
карточек, историю и сохранённые файлы. Полный запуск и восстановление
на облачной VM ещё требуют проверки в целевом окружении.
